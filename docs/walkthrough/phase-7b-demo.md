# Phase 7b Walkthrough — The demo video

> **What Phase 7b builds:** a ~2-minute narrated, subtitled video of the guard at work and the GIF at the top of the README, both generated by one command from scripts in [examples/demo/](../../examples/demo/README.md). Also the final v1 pass on the README and the report.

Design for this phase: [2026-10-25-phase-7-design.md](../superpowers/specs/2026-10-25-phase-7-design.md) (7b is §8–§9). Plan: [2026-10-25-phase-7b-demo.md](../superpowers/plans/2026-10-25-phase-7b-demo.md).

---

## 0. Why this phase exists

An interviewer with the repo open wants to *see* the claims: a message with an Aadhaar number goes in, placeholders go out, the real values come back. A screen recording made by hand can't be checked or redone, and nobody can tell how many takes it took. So the video is **built**, like the reports are: from a committed recording, by a script anyone can rerun.

The spec's anti-goals apply here too: no number in the video that isn't in a committed report, and no real API key anywhere, on screen or in git.

---

## 1. First, a feasibility check

The pipeline uses three tools new to this project. Before planning, each was tried on the laptop:

- **VHS** (in Docker, `ghcr.io/charmbracelet/vhs`) films a terminal from a script (a `.tape` file). Box-drawing characters, colours and `₹` render correctly.
- **ffmpeg**: not installed on the laptop, but the VHS image includes ffmpeg 7.1 with libass (the subtitle renderer). Nothing to install.
- **Kokoro**, an open text-to-speech model (82 M parameters, Apache-2.0), runs on CPU through `kokoro-onnx` in a slim Python container, about 2.4× faster than real time. The author listened to four voices and chose `af_heart`.

---

## 2. The big decision: record, then replay

Two ways to make the video were on the table:

| | How | Problem |
|---|---|---|
| A | Run the demo live inside VHS, calling the LLM on every render | Each render gets a different reply (a box can overflow, a provider error breaks the take); the API key has to go into the recording container; nothing to check the video against |
| **B** ✅ | **Record one live run to a file, then film a replay of that file** | The replay must be labelled honestly |

The author chose B. The recording is [examples/demo/session.json](../../examples/demo/session.json): for each scene, what the app sent, what left the machine, what the model sent back (chunk by chunk, with timings), what the app got, and the guard's log line. Every request scene in the video carries the label "recorded live: Groq openai/gpt-oss-120b, 2026-10-25 · replay of session.json".

What B buys: the video can be rebuilt any number of times for free (no LLM calls), the key never goes near the video tools, and an interviewer can open the JSON and check every frame against it.

---

## 3. The files, in pipeline order

### 3.1 `scenes.py`: what the demo says

Nine scenes, in order: `title`, `one_line`, `core`, `stream`, `secret`, `lookalike`, `log`, `results`, `outro`. A scene with `messages` is sent through the guard; the rest are drawn from the session alone. All personal data is made up:

- `core`: a support message with a name, an Aadhaar number (passes the Verhoeff checksum), a UPI ID, a phone number and a full address.
- `secret`: a pasted config with `DB_PASSWORD=...`. Deliberately a password, not a provider-style key: the session is committed, and GitHub push protection flags real-looking provider keys (it blocked a push in Phase 3).
- `lookalike`: `OTP 411038` (a real PIN code, but after "OTP" it is not an address) and a 12-digit order number that fails the Aadhaar checksum.

Tests run the real rule detector on this data, so a detector change that breaks the demo fails CI.

### 3.2 `tap.py`: the wire tap

The video's middle box is "WHAT LEFT YOUR MACHINE". To show that honestly, something has to sit on the guard's connection to the LLM and record it. The tap is an `httpx` transport wrapped around the guard's real one, passed in through `create_app(settings, transport=...)`, the same hook the tests use. So the guard code is exactly the production code.

```python
body = json.loads(request.content or b"{}")
record = {"messages": body.get("messages", []), "status": 0, "chunks": []}
```

It reads only the JSON body: **never headers**, so it never sees the `Authorization` header with the key. For streamed replies it parses the server-sent events with the guard's own `SSEParser` and keeps each content delta with its arrival time. That's how the video can show `[`, `PHONE`, `_`, `1`, `]` arriving as separate pieces.

### 3.3 `record.py`: making the recording

It starts the real guard on a free local port in a background thread (uvicorn), with the tap around its upstream connection, and drives it with the **official OpenAI SDK**, the way an app would. It also collects the guard's log lines through a logging handler.

Two safety nets:

1. Before writing, it checks the API key does not occur anywhere in the session: `refusing to write: the API key appears in the session`. A test proves it with a fake provider whose error message echoes the `Authorization` header back.
2. After writing, it runs `verify_session` (next section) and exits with an error if any claim fails.

The recording against Groq passed every check on the first attempt.

### 3.4 `session.py`: keeping the narration honest

Every claim the narration makes is a check on the recorded session:

| Narration says | `verify_session` checks |
|---|---|
| every value is now a placeholder | no highlighted value appears in anything sent upstream |
| the reply comes back with the real values put back | at least one real value is in the reply, and no placeholder is left |
| the placeholder arrives split across chunks | some placeholder spans two or more streamed chunks |
| nothing is sent to the model | HTTP 400 and no upstream request at all |
| both go through unchanged | the message sent upstream equals the one the app sent |
| the log has counts, never values | the log line has findings and contains none of the values |
| higher F1, far fewer false alarms than Presidio | true in the results block |

The narration also describes instead of quoting ("the reply comes back with the real values put back in"), so it stays true for any reply the model writes. If a recording fails a check, it is recorded again; the narration is never bent to fit it.

### 3.5 `player.py`: drawing a scene

It draws one scene from the session as labelled boxes, in colour: sensitive values yellow, placeholders green, a blocked request red. It is **standard library only**, because it runs on the VHS image's own Python (3.13, no venv), and a test checks every import against `sys.stdlib_module_names`.

Two details:

- **Wrapping keeps colours.** `paint()` works out colours on the whole text first, then wraps it, so an address that wraps onto a second line stays yellow on both.
- **Long replies are cut, visibly.** A box over its line budget ends with `… (full text in examples/demo/session.json)`. A test with a 3,000-character reply checks every scene still fits the 108 × 22 screen.

The screen size was measured, not guessed: at font size 20 the terminal had only 21 rows, so the plan's fallback (font 18: 110 × 23, minus a margin) was used.

### 3.6 `narration.md` and `voice.py`: the voice

The narration is plain text: a `## <scene>` heading per scene, one sentence per line. Each line is one subtitle, one spoken sentence, and one "beat" (the next box appearing). Tests check that every scene has narration, that there are enough lines for its beats, that it fits two minutes (309 words), and that the results narration states no numbers. The numbers on that screen are read from `data/eval/presidio-test.json`.

`voice.py` runs in its own Docker image (`voice.Dockerfile`). It reads each line with Kokoro and writes one WAV per scene plus `timings.json` (where each sentence starts and ends). The model files are downloaded with pinned SHA-256 checksums, so a changed download fails the build instead of quietly changing the voice.

### 3.7 `timeline.py` and `build.py`: one command

`python -m examples.demo.build` does everything:

1. **Narrate:** the voice image reads the script (about 105 s of speech).
2. **Plan:** each scene lasts *its narration + 0.8 s*, so one scene's voice can never run into the next, and each beat appears when its sentence starts. From that plan: the subtitles (`demo.srt`) and one VHS tape per scene.
3. **Film:** VHS films each scene's tape.
4. **Join:** ffmpeg stretches each clip to its planned length, joins them, adds a 120 px band under the terminal, burns the subtitles into the band, and lays the voice track on top. Then it cuts the `core` scene into the README GIF (0.4 MB).

**Why one clip per scene (a snag found while building).** The first full build came out 111 s long against a planned 115 s. A test with an on-screen clock showed why: VHS films a 20-second sleep as 19.4 seconds, because it drops a few percent of frames on a busy laptop. In one long clip that error adds up, and by the end the picture was ~3.5 s ahead of the voice. Filming each scene separately and stretching it back to its planned length keeps every scene in sync. The finished video is 114.6 s; the leftover 0.4 s doesn't build up across scenes.

**Checking sync without listening.** Claude can't hear audio, so the "no narration runs into the next scene" rule was checked from the audio itself: ffmpeg's silence detector on the voice track confirmed that every scene boundary falls inside silence. One frame per scene was also looked at for layout. The author should still watch the video once.

**Your own voice.** `--voice-dir DIR` takes `<scene>.wav` files and uses them instead of Kokoro's, scene by scene. If one is too long for its scene, the build stops and says which scene and by how many seconds. The subtitles stay as written, so a voiceover should follow the script.

## 5. Interview Q&A

**"Isn't a replayed demo faked?"**
It is a replay of a real run, labelled as one on screen, and the run is committed: `examples/demo/session.json` holds exactly what the app sent, what the tap saw leave the machine, what the model streamed back, and what the app got. Anyone can rerun `python -m examples.demo.record --upstream groq` and compare. Filming live would get a different reply every render, put the API key inside the recording tool, and leave nothing to check against.

**"How do you know the narration is true?"**
Each claim is a function (`verify_session`) run on the recording, both when it is made and in CI on the committed file. The narration describes instead of quoting the model, so it stays true for any reply.

**"How do you know the key never leaked?"**
Three layers: the tap never reads headers; the recorder refuses to write a session containing the key (tested with a provider that echoes the key in an error); and the repo was searched for the key's value before committing (zero files). The key comes from an environment variable and is never printed.

**"Why VHS in Docker and not a screen recorder?"**
It is scripted and repeatable: the video is built from files in the repo, so a change to the guard or the narration means rerunning one command, not re-recording by hand. Docker means nothing to install, and the same image provides ffmpeg.

**"What went wrong while building it?"**
VHS drops frames under load, so a single long clip ran ahead of the voice by ~3.5 s by the end. It was diagnosed with an on-screen clock, and fixed by filming each scene separately and stretching each clip back to its planned length. Smaller ones: a Dockerfile `--chmod` applied to the folder as well as the files (the model became unreadable), and subtitles that wrapped to three lines and reached into the terminal area, now capped at two lines by a test.

**"What does CI check?"**
The plain test job checks the scenes, the session checks, the player (including that it fits the screen and uses only the standard library), the narration and the timeline. The name-model job also records a complete session against the mock LLM through the real guard and verifies every claim, so the demo can't silently break. CI never runs VHS or Kokoro.
